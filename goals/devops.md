# Learn DevOps

**Slug:** `devops` (matches `work/devops/`)

**One sentence:**
Become an SWE who can design software, ship and run it (cloud and on-prem), and design the workflow around it — including training others — so the system still works when I leave.

**Why this, now:**
I am a SWE (9–5): backend, some frontend, some LLM features, architecture and databases. AI has shrunk how much raw coding I do, so I need a wider skill that still supports that role. I have designed systems and touched AWS, but I am not strong at infra. DevOps here is that missing half: how software is built, made safe, put on machines, and kept runnable by people, not only by me. The day job is the main practice arena: learn from what I already do, and where I can, shift work toward ship / run / observe / change / teach — then write it down. It serves the global product-company job. Until January the method is the DevOps Handbook, plus practice on the internal document tool (run and handoff). Not an AWS certificate, and not a second stack.

**What “done” looks like:**
I can take a system I would design as an SWE and run the loop myself: build → ship → run → observe → change, on a cloud path and on a server I own. Change is safe enough that I can roll back and see health, not hope. The workflow (how we change, review, and learn from the running system) and enough training/docs exist that someone else could keep it going without me. I have done this, not only drawn it — including in real work, not only in side study.

**What I will not chase in the name of this goal:**
A DevOps/SRE job title, cert collecting, or a catalog of tools I have not run. Company-wide org design, hiring systems, or “how teams grow” disconnected from a system I am actually shipping. Architecture-only work with no deploy, no operation, and no one else able to run it. Counting a normal SWE day as learning with no notes/practice file.
